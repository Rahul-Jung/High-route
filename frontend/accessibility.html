What we are aiming at

WCAG 2.2 Level AA. This page says where the site is against that, honestly, including where it falls short.

This site has not had a formal accessibility audit and has not been tested with real assistive technology by the people who use it. Everything below is the result of building to the standard and testing with automated tools and a keyboard, which catches a great deal and is not the same thing as being usable. Treat the claims as "built for" rather than "verified as".

What has been done

Structure and navigation

  • A skip link, first in the tab order on every page, jumping to the main content.
  • Semantic landmarks — header, nav, main, footer — on every page.
  • One h1 per page and headings in order, so a screen-reader user can navigate by them.
  • Dropdown navigation whose top-level items are real links to real pages, not href="#". A menu parent that goes nowhere is unusable by keyboard and on touch; this site had several and they are gone.
  • Breadcrumbs on every section page.

Keyboard

  • Visible focus outlines on every interactive element, specified rather than left to the browser default — the default outline disappears against a dark green surface.
  • Itineraries and FAQs are built on native <details>, so they are keyboard operable and announced correctly without any JavaScript.
  • Filters are real checkboxes and selects in a <fieldset> with a legend, not divs with click handlers.

Forms

  • Every field has a real <label>.
  • Errors are announced through a live region and tied to their field with aria-invalid and aria-describedby — colour alone is never the message.
  • Focus moves to the first field with a problem on a failed submit.

Content and colour

  • Body text and secondary text meet AA contrast on their backgrounds. Twenty colour pairs were computed rather than assumed, and two failed and were changed: the muted text colour was 4.3:1 (which only passes at large sizes) and is now 5.41:1, and white on the brand accent was 3.63:1 on solid buttons — fine for large text, but a button label here is 14px bold, so it needed 4.5:1. Buttons now use a darkened accent at 4.91:1 while every non-text use keeps the brand colour.
  • Availability is never colour alone — the pip always has text next to it.
  • Images have alt text; decorative images have empty alt and are hidden from assistive technology.
  • prefers-reduced-motion is respected, which switches off the card and image transforms.
  • Data tables become stacked rows at narrow widths rather than scrolling sideways — a departure date list is the one thing on a trip page a phone user definitely needs.

How it has been tested

  • Keyboard-only navigation of every page.
  • Automated checks for heading order, labels, alt text, landmark structure and tag balance, run against every page as part of this build.
  • Contrast ratios calculated for every text colour against every background it is used on.
  • Layout written mobile-first, with every media query widening the base rule rather than undoing a desktop grid. Breakpoints at 560, 600, 640, 720, 760, 860, 980 and 1040px.
  • Every page rendered with JavaScript disabled, to confirm it degrades to something honest rather than to an empty div.

Not done: testing with NVDA, JAWS or VoiceOver by a regular user of them; testing with voice control or a switch device; testing at 400% zoom in every browser; and measuring reflow at 320px in a browser (see Known problems).

Known problems

Listed because they are real, not because they are comfortable:

  • Most page content needs JavaScript. Departures, prices and availability are loaded live, so with scripting off those pages show an explanation and a working link rather than the content. The explanation is deliberate — stale prices baked into the HTML would be worse — but it is still a barrier.
  • The elevation chart on a trip page is a canvas and is not accessible to a screen reader. The same figures are in the itinerary text beneath it, which is a mitigation rather than a fix.
  • No formal audit, and no testing with real assistive technology by its users.
  • Photographs are decorative and their alt text is generic. Several would benefit from a real description.
  • Google Fonts is loaded from a third party, so a slow or blocked font request affects text rendering.
  • Long informational pages have no in-page progress indication beyond the contents list.
  • Reflow at 320px has not been verified in a browser, and one thing makes that worth saying out loud: the stylesheet sets overflow-x: hidden on the body. That means horizontal overflow is clipped rather than prevented — the page will never scroll sideways, but if something is too wide at 320px its right-hand edge is simply cut off and unreachable, which is worse than a scrollbar. The layout is built mobile-first and should reflow, but "should" is not "does", and until it has been measured this belongs on this list rather than on the one above.

Telling us

If something here does not work for you, tell us — what you were trying to do, what happened, and what you were using. That is more useful than any audit, and an accessibility problem is a defect like any other.
